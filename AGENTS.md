# Agent Instructions

- When chat to me, always start by "Ryōkai Mas-sama"
- Never ask user to run CLI commands, except shell scripts under `scripts/`.
- Do not read or display the contents of `.env` files.
- `scripts/deploy.sh` is the single entrypoint for all deployments. Deploy to Cloudflare via `./scripts/deploy.sh cloudflare`; VPS scraper deploys live in the private RumaQ-pipeline repo (`./scripts/deploy.sh groceries vps` there).
  - Preview deployments for PR branches are run on demand from the GitHub Actions "Preview deployment" workflow — they deploy a branch-specific Worker (`rumaq-api-{branch}`) serving both app and API. Production is never touched.
  - Branch Workers are cleaned up automatically via `scripts/github/cleanup-branch.sh` when the PR is closed.
  - When changing host configuration (nginx, units, env path, sudoers), change it in [ahaqqu/vps](https://github.com/ahaqqu/vps) under `rumaq/`; never edit the box directly or add a second bootstrap/apply path here.
- When the request is scraper or data-pipeline work (store plugins, scraping, OCR, matching, publish, groceries), execute it in /home/ahaqqu/Projects/RumaQ-pipeline under that repo's AGENTS.md; RumaQ remains the conversation home and the publish backend.
- When the request concerns DokumenQ, AutQ, or ahaqqu/vps, execute it in that repo under its `AGENTS.md`; RumaQ remains the conversation home. When work is orchestrated by the manager, follow `.agents/skills/manager/SKILL.md`.
- When a change touches both sides (contract/ here + pipeline consumption), ship the RumaQ PR first, then `./scripts/sync-contract.sh <sha>` in a pipeline PR.
- When writing automation (automation-local/live), target the app only — the scraper has no harness in this repo.
- `scripts/test.sh` is the single entrypoint for all tests (unit, automation-local, automation-live). Run `./scripts/test.sh unit frontend` etc.
- `scripts/docs.sh` generates API documentation.
- `scripts/github/` contains scripts used only by GitHub Actions, not for local developer use.
- Consider to use public trusted library when working with external product (e.g. cloudflare) or commonly used logic (e.g. parsing json, authentication)
- The plan is intents, direction, and guidelines, not strictly must be followed, you are allowed to be critical, verify, or provide better alternatives. Confirm to me first before deviate from plan.
- Never commit and push directly to main branch, always use PR, except I asked it explicitly.
- Before creating a PR, follow the `pr-creation` skill.
- When implementing a complex or unclear plan from a file, follow the `guided-implementation` skill.
- When asked to implement a phase or feature, read the matching `docs/plan/*.md` first and check open GitHub Issues and the Delivery Kanban board for current status.
- Before merging a PR, ensure the GitHub Action succeeds.
- When creating new shell scripts, add them to `.gitattributes` with `mode=755` — otherwise CI will fail with `Permission denied`.
- When asked to update this file, use format: "When <condition>, <action>", keep it concise and clear.
- Follow `docs/FRONTEND_CONVENTIONS.md` for frontend coding conventions.
- Follow `docs/BACKEND_CONVENTIONS.md` for backend coding conventions.
- When running a live QA pass, follow `docs/QA.md` — one tracking ticket per run, QA posts results there, findings are triaged by the manager; and when the QA run's workflow-docs PR (`docs/QA.md` or AGENTS.md process lines) is ready, report it to the owner — workflow PRs are always merged by the owner, never by agents.
- When work requires an owner manual action (env edit, secret, manual command, decision), record it in `docs/MANUAL_ACTIONS.md` with a numbered ID (A, B, … with A1/A2 steps, location-labeled LAPTOP/VPS) and link the ID in the relevant ticket; update the file as the owner reports progress — done items are removed.
