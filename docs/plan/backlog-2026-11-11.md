### 7.1.1 CPU / memory / stability context

The three runtime crashes earlier on 2026-11-11 were root-caused to uncapped automation containers saturating the laptop; since #594 merged (compose caps: api 1.0 CPU/768 MB, test-runner 2.0 CPU/2 GB + 1 GB shm, proxy 0.25/128 MB) the same night sustained a 46-min QA agent, four concurrent automation-local runs and two review waves **with zero crashes**. Agent processes themselves are API-bound and light; CPU/RAM peaks come from test suites and builds, i.e. from what agents _invoke_, not from the agents.

### 7.2 Improvements to adopt (token → time → CPU/memory)

1. **Narrow-first gate discipline (token, biggest lever).** Authors iterate on the single affected test file (`bun test backend/src/…/receipts.test.ts`), then run the full `./scripts/test.sh unit backend` once before opening the PR. Tonight's authors ran the full suite 3–4× per PR; that is most of the 5.5M/PR. Target ≈3M/PR.
2. **Brief shortlists, not discovery (token).** Every brief names the exact files/PRs to read (author briefs now do); reviewers get a "files unchanged from your prior waves — do not re-read" note on resume.
3. **Resume-first protocol (token + time).** Always try `SendMessage` resume before a fresh dispatch — it re-pays only the delta. Caveat recorded: agents whose harness registry died in a crash are unresumable; the push-after-every-commit rule bounds that loss.
4. **Batch reviews, keep depth tiering (token + time).** One thermos reviewer per wave, normal depth for docs-only (#615), and PR bodies carry the evidence so reviewers verify rather than re-derive.
5. **Read-only analysts for survey work (token).** Anything that produces a decision document (portfolio scoring, research, incident write-ups) runs as a read-only analyst; writers are reserved for code+gates.
6. **Complementary-slot pairing (CPU/memory).** When both slots run, pair a gates-heavy author with a read-phase agent (analyst/reviewer-between-batches). Never two full-suite phases at once on the laptop; builds and bun test workers are the actual CPU/RAM spikes.
7. **Worktree hygiene (disk → memory pressure → CPU).** After merge: remove the worktree + branch; evidence stays in the manager journal and GitHub. Tonight accumulated 13 worktrees × node_modules ≈ several GB.
8. **Cost ledger per wave (visibility).** The journal records per-agent tokens/tools/wall for every dispatch; cost-per-merged-PR tonight ≈ 7–8M tokens (author + amortized review). Re-baseline after the 7.2 items land.
9. **Measure before tuning (CPU/memory).** The only proven CPU/RAM lever so far is #594's compose caps. Before bounding bun-test workers or cargo parallelism further, capture one baseline (`/usr/bin/time -v` on a full unit run) — a ticket can hold the numbers.
