## Resume protocol

1. Work in a dedicated worktree for each implementation slice; never commit directly to `main`. In Phase 2 the slices stack (addendum §8): the first slice of a stack branches from `main`, slice N+1 branches from slice N and targets N's branch while the earlier pull request is held, and the stack is rebased whenever `main` moves.

3. `gh pr view 759 --comments` and `gh issue view 758 --comments` hold the planning record; `gh issue view 763 --comments` holds the Phase 2 design record (design review, addendum, owner confirmations); each slice issue holds its own implementation decisions.
4. Execute only the **Next action** below. C0 is signed, so Phase 2 is open and its design is confirmed; C1 and later gates are **not** signed, so do not start Phase 3 design work, any paid model call, publication, scheduling, or household module early.
5. Before stopping: commit, push, and update **Current gate**, **Next action**, and **Log** in this file.

Working state lives in git and GitHub. Harness-local state (`~/.agents/manager/...`, chat history, local inboxes) does not travel between harnesses, models, or machines.

**Decisions — final (owner, 2026-11-28; addendum §1 and §9):**

- **Vocabulary first, not the contract major.** The first contract work is the domain vocabulary kernel (R3); the pipeline-facing wire contract is cut once, after R9 and before Phase 4.
- **`server/` is v2's home** — a new top-level directory, a standalone Bun package with its own `bun.lock`. The root `workspaces` list does not change; the earlier word "workspace" is superseded. R2 is the gate: if the type-checker cannot handle the nested package after one bounded attempt, `server/` becomes a root workspace member instead. `web/` arrives in Phase 3; legacy `backend/` and `frontend/` stay frozen until Phase 10.
- **Contract location C.** Legacy `contract/` is untouched. The kernel starts as a pure TypeScript + Valibot subtree of `server/`, behind a purity test, and is promoted to a package at the wire-contract cut.
- **PostgreSQL gate: `./scripts/test.sh unit server`** — a real PostgreSQL 17 with pgvector and pg_trgm, connected as the real `rumaq_app` and `rumaq_migrator` roles. It fails rather than skips without a database and runs inside the required `ci` check. The suite exists from R2; its AGENTS.md line lands with it.
- **Capacity gate.** A bounded synthetic-load baseline on the host in Phase 2; the combined stress test moves to Phases 6–7.
- **Backup scope (vps V5).** A nightly encrypted dump and an isolated restore drill in Phase 2; WAL archiving is a separate decision before Phase 6, when scheduled operation gives it a real recovery-point objective. No cluster-wide PostgreSQL change in Phase 2.
- **Database bootstrap (vps V1).** A one-time runbook step — a reviewed, idempotent SQL file in `ahaqqu/vps`, a runbook section and a CI test on a throwaway database — run once by the owner. No applier feature; a confirmed deviation from "host config in a manifest row".
- **v2 API hostname for Phase 2 (vps V3).** A new DNS-only name (working name `rumaq-v2.ahaqqu.com`; the owner may still rename it before V3's plan). Neither existing RumaQ hostname changes in Phase 2. Not Cloudflare-proxied in Phase 2, so the real-client-IP rule is not deployed by V3; it is rehearsed before the main-host cutover in Phase 3.
- **Dependabot during the freeze.** Auto-merge only patch-level updates — security and patch bumps keep flowing; minor and major bumps of the frozen v1 wait for the owner's approval. Its own small workflow PR: `.github/` only, which is in the deploy skip set, so merging it does not deploy the v1 Worker.
- **Data model.** `source_tiles` is a table. `published_current` is a pointer table whose primary key is `offer_id`. `offers` are keyed by source lineage `(source_tile_id, source_line)` — the same product at the same store in two overlapping campaigns is two offers and two cards, and the product page shows both.
- **Migrations.** A migration runner inside the server artifact (not a library), run by a third one-shot unit, `rumaq-migrate`, with its own OS user and env file.
- **Test database.** `pgvector/pgvector:0.8.0-pg17-trixie`, tag-pinned: the host's pgvector minor and Debian line, so CI tests what production runs.
- **Action T is closed.** The prepared `rumaq-v2` D1 (`f1b4a711-f4a2-4dc9-8550-2b12f37ca6d7`) is unused; deleting that empty database is a separate, later decision (Phase 10).
