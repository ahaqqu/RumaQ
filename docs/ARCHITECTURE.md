# RumaQ — Full-Stack Architecture

This document describes the production architecture for RumaQ on Cloudflare's free tier. It is designed for a single household (MVP) but keeps the data model ready for multi-household expansion.

> **Testing strategy has moved** → [`docs/TEST_STRATEGY.md`](TEST_STRATEGY.md)

> **API caching plan (recently implemented)** → [`docs/plans/workers-cache-plan.md`](plans/workers-cache-plan.md)

## 1. Goals & constraints

- **Low friction.** Users photograph receipts; the system infers stock. Manual logging is a fallback, never the default.
- **Cheap to run.** Everything sits on Cloudflare's free tier (Workers with static assets, D1, R2).
- **Privacy first.** Users bring their own AI key. The backend stores it encrypted and only uses it on their behalf.
- **Fast and local-feeling.** The API edge is close to users; the UI stays optimistic and shows loading states that name the work.

## 2. High-level stack

| Layer          | Service                                | Role                                            | Free-tier limit                     |
| -------------- | -------------------------------------- | ----------------------------------------------- | ----------------------------------- |
| Frontend       | Cloudflare Worker (static assets)      | Hosts the React + Vite SPA on the Worker origin | Bundled with the Worker deploy      |
| API            | Cloudflare Workers                     | Hono HTTP API, auth, AI proxy                   | 100,000 requests/day                |
| Database       | Cloudflare D1                          | Relational SQLite database                      | 500 MB storage, 100,000 queries/day |
| Files          | Cloudflare R2                          | Receipt image storage                           | 10 GB storage, 10 M reads/mo        |
| Cache/metadata | Cloudflare KV (optional)               | Rate-limit counters, AI usage windows           | 1 GB, 100,000 reads/day             |
| Auth           | Google OAuth 2.0                       | SSO login, managed inside the Worker            | Free                                |
| AI             | OpenAI / Gemini / Anthropic / OpenCode | External LLM calls proxied through the Worker   | User's own billing                  |

```
User browser
    │
    ▼
App + API on one origin — Cloudflare Worker with static assets
(rumaq.ahaqqu.com or rumaq-api-{branch}.rumaq.workers.dev)
    │
    ├── /api/* ──► gateway (same origin, no CORS)
                            │
                            ▼
                    [default entrypoint — gateway]
                            │
                    ┌───────┴──────────┐
                    ▼                  ▼
              /api/auth/*        /api/* (all others)
              (handled directly   │
               in gateway,        │
               never enters       │
               CachedApi)         │
                    │             │
                    ▼             ▼
                    [CachedApi entrypoint]
                    ┌─────────────┼──────────────┐
                    ▼             ▼              ▼
              public GET    public GET      authenticated
              /api/health   /api/auth/      /api/me
                            email-status    /api/stock
              (Cache-Control:  (Cache-Control:  (Cache-Control:
               public,          public,          private,
               max-age=60)      max-age=60)      no-cache)
```

### Auth routes

Auth paths (`/api/auth/login`, `/api/auth/callback`, `/api/auth/logout`, `/api/auth/email-login`) are handled directly in the gateway via `authApp.fetch()`. They never enter the cached entrypoint.

### Caching

- **Public routes** (`/api/health`, `/api/auth/email-status`): `Cache-Control: public, max-age=60`
- **Authenticated routes** (`/api/me`, `/api/stock`, etc.): `Cache-Control: private, no-cache` — never cached at the edge, every request runs through the Worker to verify auth.
- **Error responses**: `Cache-Control: private, no-cache`

Receipt images flow through the Worker into R2. The Worker returns signed URLs so the frontend never talks to R2 directly.

## 5. Authentication

Google OAuth 2.0 is implemented inside the Worker using the [Authorization Code flow](https://developers.google.com/identity/protocols/oauth2/web-server) with PKCE.

1. `GET /api/auth/login`
   - Generates a `state` nonce and PKCE `code_verifier`.
   - Stores the verifier in a short-lived signed cookie.
   - Redirects the browser to Google's authorization endpoint.

2. `GET /api/auth/callback`
   - Validates the `state` parameter.
   - Exchanges the authorization code for an access token.
   - Fetches user info (`email`, `name`, `picture`, `sub`) from Google's userinfo endpoint.
   - Upserts the user in D1.
   - Issues a long-lived signed JWT in an `HttpOnly`, `Secure`, `SameSite=None` cookie named `rumaq_session`.

3. `GET /api/auth/logout`
   - Clears the session cookie and redirects to the app origin.

4. Protected-route middleware
   - The **gateway** (`backend/src/gateway.ts`) routes `/api/*` non-auth requests to the `CachedApi` entrypoint (which wraps `apiApp`).
   - Inside `apiApp` (`backend/src/apps/api.ts`), the `propsAuthMiddleware` first checks `c.env.props` (fast path when props are provided), then falls back to reading the `rumaq_session` cookie, verifying the JWT, and looking up the active household from `user_settings.active_household_id`. It sets Hono `Variables` (`userId`, `householdId`) for downstream route handlers. Routes that require authentication register this middleware; public routes skip it entirely.

**Why not Cloudflare Access?** Access is simpler, but in-app OAuth keeps the API self-contained, lets us store the user record in D1 for personalization, and makes local development straightforward with the Cloudflare Vite plugin.

### Email/password auth (testing mode)

A second auth method is available for testing, gated behind the `EMAIL_AUTH_ENABLED` env variable. Google OAuth remains the primary production path.

1. `GET /api/auth/email-status`
   - Public endpoint returning `{ enabled: boolean }` so the frontend can decide whether to render the email form.

2. `POST /api/auth/email-login`
   - Enabled only when `EMAIL_AUTH_ENABLED === 'true'` (otherwise returns 403).
   - Validates `email` + `password` against the `password_hash` column on the `users` table (PBKDF2-SHA256, 100k iterations).
   - Onboards a new user with the same household/seed logic as the Google callback.
   - Issues the same `rumaq_session` JWT cookie.

### Admin access

Operator-only surfaces (`/api/admin/*`: the price monitor, Scrape Now queue, match review) are gated by the `requireAdmin` middleware, which reads `users.is_admin` (migration 0014) — the flag is the single source of truth and there is no environment fallback. `/api/me` exposes it as `isAdmin`.

Grant or revoke with a one-statement SQL runbook against the production D1 database; no redeploy is needed because the flag is read per-request. Matching folds case (`lower(email)`) because the OAuth callback stores the Google-provided email verbatim:

```bash
# grant
cf d1 execute rumaq --remote --command "UPDATE users SET is_admin = 1 WHERE lower(email) = lower('…');"
# revoke
cf d1 execute rumaq --remote --command "UPDATE users SET is_admin = 0 WHERE lower(email) = lower('…');"
```

One-time cleanup after this ships: the former `ADMIN_EMAILS` Worker secret stops being read but `scripts/deploy.sh` never deletes secrets — remove it manually with `cf workers secrets delete ADMIN_EMAILS`.

## 6. Database

Cloudflare D1 runs SQLite at the edge. The schema is relational and normalized so the same Worker can serve a single household today and multiple households later without rewrites.

See [`backend/migrations/0001_schema.sql`](../backend/migrations/0001_schema.sql) for the full DDL.

Core entities:

- `users` — Google-authenticated accounts.
- `households` + `household_members` — one or more households per user.
- `locations`, `stores` — household-scoped lookup lists.
- `items` — canonical product catalog inside a household.
- `stock` — current on-hand quantity, expiry, run-out estimate.
- `purchases` + `purchase_items` — receipt history; the substrate for all estimates.
- `plans` + `plan_items` — AI-generated shopping trips.
- `user_settings` — AI provider/key, motion preference, currency, and persona roles.
- `ai_usage_events` — one row per completed AI call (provider, model, input/output/cached tokens, key source); auto-deleted after one year by the daily retention cron.

## 7. AI integration

Users supply their own API key in Settings. The frontend sends it to the Worker, where it is encrypted with `WORKER_ENCRYPTION_KEY` (AES-GCM via Web Crypto) before being stored in D1. The Worker decrypts it only when making an AI call on the user's behalf.

AI lanes (MVP):

1. **Receipt → stock.** Image uploaded to R2; Worker sends the image URL + prompt to the user's chosen LLM and returns parsed line items for confirmation.
2. **Plan a trip.** Worker asks the LLM to build a shopping plan from low stock + expiry + history.
3. **Chat assistant.** The Worker proxies a chat request; the system prompt includes the user's persona setting.
   > **Tech debt:** Streaming is deferred. The current implementation returns the full response body. See `backend/src/lib/chat.ts` — `sendChatMessage` calls `completeText` (completion, not streaming). The persona system prompt is EN-only (single locale); see `backend/src/lib/persona.ts`.

Every completed AI call is recorded as one row in `ai_usage_events` (per-call granularity — what the 24h/7d/30d admin analytics and per-user cache hit rates need). Usage never caps a call: BYOK is the norm and the shared server key (`RUMAQ_SERVER_AI_PROVIDER`/`RUMAQ_SERVER_AI_KEY`) is uncapped too (issue #353). Retention: a daily cron (`gateway.scheduled`, `cloudflare.config.ts`) deletes events older than 365 days. The user can pick the model (`ai_model`) and a thinking level (`ai_thinking_level`) per provider, mapped to each API's reasoning controls.

## 8. Deployment

### Price data pipeline (rumaq-scraper)

Grocery price data is produced by the `scraper/` workspace — a headless TypeScript/Bun port of the retired haqita pipeline (full plan: [`docs/plan/haqita-integration.md`](plan/haqita-integration.md)). The package runs on [Effect-TS](https://effect.website) (`effect` v4): modules compose `Effect` values with typed tagged errors (`Data.TaggedError`), the pipeline is `Effect.gen`, and the CLI seam keeps the nightly unit green: a failed run is logged to the journal and recorded in `status.json` with its own exit code (1 failure / 2 quota — since issue #347 the quota exit is a backstop only: a dead model chain isolates per store and exits 1), and retried by the next night's timer — seven consecutive failed nights trip the freshness gate instead (owner decision 2026-10-27: one bad run must never read as "service down"):

- Superindo brochure pages are scraped with plain fetch (realistic Chrome headers, cookie jar, retry ladder), filtered for novelty by URL+MD5 state so unchanged pages are downloaded once per run (the bytes are needed to compute the MD5) but never re-OCR'd or re-published. Every outbound request has a per-attempt timeout (30s fetch / 60s ingest POST) so a stalled peer surfaces as a retryable transport error instead of hanging the unattended daily job, and permanent 4xx (everything but the transient 429/408/425) fails fast without burning the retry backoff.
- Lotte Mart sits behind Imperva Incapsula: its listing page rides the Tier-2 browser ladder (headless Chromium via `playwright-core`, realistic UA/viewport/locale, one session per store run, tabs per page) while brochure images download over plain fetch — the CDN is not challenge-protected. If the browser tier itself gets the interstitial (tiny page + Incapsula markers), that is a Tier-3 per-store-proxy decision, not a retry. Until proxy credentials are configured (`LOTTE_PROXY_URL` in the VPS env file), that state is first-class: the pipeline marks the store `needsProxy` and keeps the run green — the monitor shows the amber per-store gap instead of a red failed store every night. With credentials set, a persisting challenge is a real failure again. `scraper/scripts/check-lotte.ts` remains the plain-fetch reachability probe for the tier decision from a given egress IP, probing both the global header set and haqita's actual Lotte override. haqita itself scraped Lotte with plain requests and no browser, but that success was egress-IP-dependent, not header-dependent: a 2026-10-28 probe replaying haqita's exact client (python-requests) and headers (`Accept-Language: en-US,en;q=0.5`, kept verbatim as Lotte's `headerOverrides`) still received the Incapsula challenge from a Jakarta Telkom residential IP — headers alone do not lift the challenge.
- The Tier-3 free proxy is a **reverse SSH tunnel to the operator's home box** (validated 2026-10-28: browser traffic from the VPS through the tunnel egresses as the home residential IP and clears the Incapsula challenge, which the VPS's Vienna datacenter IP never does). The home box runs two root-free user units — `lotte-connect-proxy` (a minimal loopback CONNECT proxy, `~/.config/lotte-tunnel/proxy.py`) and `lotte-tunnel` (`ssh -N -R 127.0.0.1:18080:127.0.0.1:3128`, keepalive loop, dedicated `lotte_tunnel_ed25519` key restricted on the VPS to `permitlisten=127.0.0.1:18080`); `Linger=yes` keeps them alive across reboots without a login session. Enabling the pipeline side is an operator edit of the root-only `/etc/rumaq/scraper.env` (`LOTTE_PROXY_URL=http://127.0.0.1:18080`) plus a unit restart — env files are operator-owned bytes, so no repository script writes them. If the home box is down at the 23:00 UTC fire time, the store fails visibly (transport error, red run) and recovers the next night — Superindo is unaffected.
- Astro (astronauts.id, quick-commerce) is the first **catalog-kind** store: no images and no OCR — its category pages server-render the inventory JSON inside the Next.js flight stream, and the plugin extracts the product objects structurally (the API's key order varies between responses, so no first-key anchor). The direct API is unusable (app-version gate `EC1001` + device-fingerprint header), and the SSR route only exposes page 0, so coverage is 30 items per category for the three staples (beras, minyak goreng, daging ayam — plan §6.1); the page list is overridable without a redeploy via the `ASTRO_CATEGORY_PAGES` env var. Catalog items flow through the same outbox → match → publish path as OCR'd items, one batch per source page.
- Hypermart (hypermart.co.id, issue #322) is the **superindo shape end to end** — plain-tier brochure pages with zero new pipeline engineering: the weekly koran on `/promo-koran/` is ~11 full-page JPGs sitting in the static WordPress HTML, harvested from both Elementor carriers (lightbox `href`s + WP Fastest Cache lazy divs) and filtered by host allowlist → `/wp-content/uploads/` path → `.jpg` extension → the `JAWA-*` basename glob, which by construction excludes the bank-promo carousel and the stale-2020 `JAWA-8.pdf` download decoy. DOM order is page order; the region picker (23 sibling pages) is a store-side navigation RumaQ ignores (ALL JAWA only). Filenames refresh **in place** weekly (`cache-control: max-age=604800`), so novelty keys on the content MD5 (`fetch/state.ts`), never the URL — the property is pinned by a same-URL-new-bytes regression test, not rebuilt (design-arch §1.1/§3).
- Indomaret (indomaret.co.id, issue #322) ships its ~10 weekly brochures as **static PDFs** behind per-brochure pages whose Real3D-Flipbook config embeds the `pdfUrl` (JSON-escaped; the global JS template's empty `pdfUrl` must never win). The plugin walks hub → detail pages → `pdfUrl` → a new gate-free `fetchDocument` (a document fetch is honest about being non-image, so the OCR download path's `NonImageContent` gate does not apply) → `util/pdf.ts`'s rasterizer — poppler's `pdftoppm` at 150 DPI PNG behind an injectable seam — and yields **pre-fetched page bytes**, so the stock classify → OCR → publish flow runs unchanged: novelty keys on the rendered bytes' MD5 (poppler PNG output is deterministic; pinned by a live test), magic-byte sniffing declares `image/png`, and the maxPages cap clamps at **render time in hub document order** (a PDF whose pages would all be dropped is never downloaded). Two loud failure modes, never silent zeros: a missing `pdftoppm` binary fails the store with a typed `PdfRenderError` naming the binary (VPS poppler provisioning is deferred to the github.com/ahaqqu/vps migration — owner directive 2026-10-30), and structural churn (zero brochure links on the hub, a detail page with no `pdfUrl`) fails with the `ScrapeStructureError` sentinel (design-arch §1.2).
- Alfamart (alfagift.id, issue #322) is the first **`catalog` + `browser`** store: a Nuxt shell whose gateway API is fingerprint-gated (FingerprintJS visitorId on every call — the API itself stays out of scope), while an anonymous headless browser renders structured promo cards. The DOM contract is anchored on the site's own **URL grammar, never class names**: `/promo/{slug}` campaign anchors on the `/promo` listing (freshest first, verified once at bring-up; the code commits to DOM listing order; the maxPages slice happens **before any detail visit**, so the Chromium budget is hard-bounded at 1 + maxPages navigations/cycle) and `/p/{slug}-{id}` product anchors whose card is found by a bounded ancestor climb (≤ 5 levels) to the nearest container carrying an `Rp` price. The post-discount price is what the customer pays; the badge `%` rides `parsePromo`'s existing discount_pct pattern with zero new parser code; within-run dedupe keys on the product href. Zero campaigns on the listing or zero cards on a campaign page fail with the `ScrapeStructureError` sentinel — a gateway 401/403 leaves no cards, so the red store is the ops signal until proxy credentials are configured. Since ≤ 2026-10-31 the gateway hard-403s datacenter IPs outright, before FingerprintJS even runs (issue #335 probes, 2026-11-01: zero promo anchors render from the VPS for 152 s+), so scraping needs residential egress — validated 2026-11-01 from the box through the existing Tier-3 lotte tunnel (`http://127.0.0.1:18080`: 109 anchors in ~18 s). Enabling it is an operator edit of the root-only `/etc/rumaq/scraper.env` (`ALFAMART_PROXY_URL=http://127.0.0.1:18080`) — env files are operator-owned bytes, so no repository script writes them. The fetch machinery grew one capability: `fetchRendered(url, { waitForSelector })` (`BrowserPage.waitFor` → `page.waitForSelector`, riding the navigation's retry engine; the plain tier aliases it away), and the latent D5 break was fixed — `processCatalogStore` forwards `options.launcher`, without which the first catalog+browser store would have booted real Playwright inside tests (design-arch §1.3/§2).
- New pages go through Gemini vision OCR (prompt ported verbatim from haqita) with a quota-aware retry policy; the page's real content type (magic bytes, then server declaration, then URL extension — clamped to the image types Gemini accepts) is threaded into the OCR call so a PNG page is never declared jpeg; invalid items land in `rejected-items.log` in the state dir. Both vision surfaces (OCR + verifier) ride a 5-rung Gemini model fallback chain (issue #347): a daily-quota 429, a 503 saturation that outlived the retry ladder, or a model-fatal 404 advances to the next rung for the rest of the run (per-run state, one journal line per advance, per-store `modelsUsed` in status.json/report); only when every rung is dead does the OCR store fail — as `ChainExhaustedError` under per-store isolation, so the run continues and the monitor reddens — while the verifier degrades to null answers as before.
- OCR'd items are matched against a persistent **canonical catalog** (`catalog.json` in the state dir) — the redesign at the heart of the port: every item resolves against the growing catalog (gates 0–3 exact/brand/token, gate 4 Gemini embeddings with an on-disk cache keyed by model, gate 5 price plausibility, gate 6 the verbatim-prompt Gemini YES/NO verifier for the ambiguous band). Confident unmatched items found new entries, so later items in the same run cross-store match against them; verifier NOs found separate entries. Embedding/verifier outages (including quota) degrade to fewer matches instead of failing the run — the OCR is already paid for. Promo text is parsed into real `promoType`/`effectiveUnitPrice` (ported promo parser; discounts apply no math because the OCR price is already post-discount).
- Extracted items are published to `POST /api/internal/ingest/prices` (bearer `HAQITA_INGEST_SECRET`) with their match outcome (`matchMethod` exact/embedding/ai, or `solo` + confidence 1.0 for first sightings — no cross-store identity claim). The pipeline defaults to dry-run until go-live (`RUMAQ_PUBLISH=true` in the env file flips the nightly job).
- Delivery is at-least-once via a publish outbox: each OCR'd image appends its items to `run-<scrapedAt>.jsonl` **before** the novelty state checkpoints that image, so a crash between the two costs at most one re-OCR of the image — never paid-for items stranded outside every outbox file. Each outbox line carries the extracting run's `scrapedAt`, so when the next run replays pending files into its payload the items keep their original `observedDate` (the ingest upsert's conflict key includes `observed_date`, making replay idempotent across days); files are retired only after a successful real publish. A store whose run dies mid-way (fully-dead model chain, `ChainExhaustedError`) keeps its already-OCR'd items pending in the outbox — they do not ride the failing run's payload and replay on the next run, while the healthy stores' items still publish that same night.
- On-demand runs (**Scrape Now**, [`docs/plan/scrape-now.md`](plan/scrape-now.md)): the admin UI queues a command in D1 (`scrape_commands`, one run at a time); a long-running `rumaq-scraper-agent.service` on the VPS polls `GET /api/internal/scrape/next` over the same bearer channel every 15s, claims it, runs `index.js --publish --stores=<slugs>` under `flock` on `<stateDir>/run.lock` (the nightly's `ExecStart` holds the same lock with `flock -n`, so a manual run and the nightly can never overlap — a collided nightly skips and retries tomorrow), streams the child's output lines back as events (idempotent by `(command_id, seq)`; the agent's ring buffer keeps the tail and flags `logTruncated`), and posts a terminal finish with the pipeline's real exit code (scoped runs, unlike the nightly, do not soft-exit). Admin reads the live log via incremental polling of `GET /api/admin/scrape/commands/:id/events?afterSeq=N`.
- The ingest contract is the single shared Valibot schema in the `@rumaq/contract` workspace package (`contract/src/index.ts`), a declared dependency of both the backend and the scraper.
- The matcher, normalizer, promo parser and gates were ported from haqita and verified by diff-testing against the original Python on identical inputs (value-identical everywhere; the one deliberate divergence: impossible OCR dates like "45 Mei" are rejected to null instead of emitting `2026-05-45`, which the contract's date regex would have accepted).

Scraper environment (VPS, root-only `/etc/rumaq/scraper.env`): `GEMINI_API_KEY` (OCR/embeddings/verifier), `RUMAQ_INGEST_URL` + `RUMAQ_INGEST_SECRET` (publish), `RUMAQ_PUBLISH=true` (live), optional `RUMAQ_SCRAPER_STATE_DIR` (defaults `./state`; `/var/lib/rumaq-scraper` on the VPS) and per-store `*_PROXY_URL` (Tier 3). `scraper/env.example` documents these variables but is non-authoritative; the host template is `ahaqqu/vps` `rumaq/env/scraper.env.example`. Local/manual runs: `./scraper/scripts/run.sh` (dry-run) or `--publish`; `--self-check` is the post-deploy gate.

The scraper's host configuration — system user, the four units, the live nightly timer, the deploy contract, the deploy identity's grant and the root-only env file — lives in [`ahaqqu/vps`](https://github.com/ahaqqu/vps) `rumaq/`, installed by that repo's root applier; this repository writes no unit, sudoers, timer or env file. Deploys are commit-based and scripted: `./scripts/deploy.sh vps` (`scripts/deploy/vps.sh`) builds `dist/index.js`, `dist/agent.js` and the real `playwright-core` package, verifies the archive (required entries, regular files only, no `browsers/`, within the contract's size caps), uploads it to `/srv/vps-incoming/rumaq.tar.gz` as `rumaq-deploy`, runs `sudo -n /usr/local/sbin/vps-deploy rumaq`, then runs the shared box sweep (`bash /srv/vps-ops/doctor.sh`) as the same identity — a missing or failing sweep fails the deploy. The helper verifies the artifact, swaps the tree, preserves the Chromium revision cache in `browsers/`, restarts the Scrape Now agent, and proves the tree runs via `rumaq-scraper-selfcheck.service` — a deploy that cannot prove the nightly job runs has not deployed. A `playwright-core` bump installs its Chromium revision from the uploaded artifact via `scripts/deploy/browser-revision.sh`, which also heals the modes the installer leaves for the service user. CI runs the same script from `deploy.yml`'s `deploy-vps` job when a main push touches the scraper's world; the job is gated on `vars.VPS_HOST`, and the cutover is complete (the `rumaq-deploy` identity holds this repository's key). The nightly timer (23:00 UTC = 06:00 WIB) is live and managed there; a deploy never enables or disables it.

### Production deployments

Production deploys to `main` are **commit-based**: `.github/workflows/deploy.yml` triggers on every push to `main` (and on demand from the Actions tab for redeploys). Its first job runs the same CI gate as PRs (`scripts/github/ci.sh`), and the `deploy` job — gated by `needs: ci` — invokes the same `./scripts/deploy.sh cloudflare` used locally. Because both jobs live in a push-triggered workflow, CI and deploy status are visible on the commit itself. Pull requests use `.github/workflows/ci.yml` instead, which has no deploy job, so PR checks never show a deploy entry.

Rapid merges queue on the `deploy-main` concurrency group and deploy sequentially. When the changes since the **last successful deploy** only touch deploy-irrelevant files (Markdown, `docs/`, `.github/`, license/attribute files), `scripts/github/needs-deploy.sh` skips the deploy — a deliberate, visible skip; anything else deploys. Basing the skip decision on the last deployed commit (queried via the GitHub API) rather than the previous push means docs-only pushes and dropped queued runs can never hide a pending code change: the next deploy's diff still contains them. Production deploys always use the `rumaq` D1 database configured by `CLOUDFLARE_DATABASE_ID`.

### Branch deployments

When not on `main`, `./scripts/deploy.sh cloudflare` deploys to a **branch-specific Worker** (`rumaq-api-{sanitized-branch}`) that serves both the SPA (static assets) and the API. This gives a branch its own real preview environment at a single URL, backed by a real Worker, rather than pointing the preview frontend at the production Worker. Previews are deployed **on demand** via `workflow_dispatch` — not every PR gets one automatically.

Pull request previews use a dedicated **staging D1 database** (`rumaq-preview`) so preview data never touches production. The preview database is created once and shared across all PR previews. Production deploys continue to use the `rumaq` database configured by `CLOUDFLARE_DATABASE_ID`.

Branch Workers are cleaned up automatically via `.github/workflows/cleanup-branch.yml` when the PR is closed. `scripts/cleanup-preview-workers.sh` deletes all `rumaq-api-*` preview Workers at once if orphans ever accumulate.

`.github/workflows/preview.yml` runs only on `workflow_dispatch`. It deploys the branch Worker and comments the preview URL on the PR when one is open for the branch.

### Custom domain

The canonical production URL is `https://rumaq.ahaqqu.com`, attached as a **Worker Custom Domain** on the `api` Worker (declared via `worker.domains` in `backend/cloudflare.config.ts`; `cf deploy` creates the DNS record and certificate automatically on production deploys). Attaching a custom domain disables the Worker's `*.workers.dev` route — `api.rumaq.workers.dev` no longer serves traffic, and nothing references it in docs, smoke tests, or the scraper ingest config.

One-time cutover steps (already performed):

1. **Migrate the zone**: add `ahaqqu.com` to the Cloudflare account and switch its nameservers away from the registrar — Worker Custom Domains require the hostname's zone to be a Cloudflare zone in the deploying account. The `kajianq.ahaqqu.com` A record was re-created as DNS-only after the import missed it.
2. **Cloudflare dashboard**: detach `rumaq.ahaqqu.com` from the legacy Pages project `rumaq` (Custom domains → remove). A hostname claimed by another project makes the Worker Custom Domain attach fail with a DNS overlap error.
3. **Deploy `main`**: `./scripts/deploy.sh cloudflare` attaches the domain to the `api` Worker.
4. **Google Cloud Console**: add `https://rumaq.ahaqqu.com/api/auth/callback` to the OAuth client's authorized redirect URIs — the callback `redirect_uri` is derived from the request origin, so Google sign-in only works for hosts registered there.

The legacy Pages project was deleted after the cutover; `rumaq.pages.dev` no longer resolves.

### One-time setup

1. Set the Cloudflare account ID:

   ```bash
   export CLOUDFLARE_ACCOUNT_ID=your-account-id
   ```

   Wrangler reads `CLOUDFLARE_ACCOUNT_ID` automatically. You can also put it in `.env` (gitignored) at the project root; `scripts/deploy.sh` sources `.env` if it exists.

2. Create the D1 database:

   ```bash
   node scripts/deploy/deploy-cf.js d1-setup
   ```

   Copy the returned UUID and export it:

   ```bash
   export CLOUDFLARE_DATABASE_ID=the-returned-uuid
   ```

   `backend/cloudflare.config.ts` reads `CLOUDFLARE_DATABASE_ID` from the environment at deploy time; never commit a real database ID.

   **Where to find the ID later:**
   - Cloudflare dashboard: Workers & Pages > D1 > `rumaq` > Database ID
   - cf CLI: `cf d1 list`
   - API: `GET /client/v4/accounts/{account_id}/d1/database`

3. Create the R2 bucket:

   ```bash
   ./scripts/deploy.sh cloudflare
   ```

   The deploy script creates the buckets if missing.

   The buckets are private by default. Verify privacy in the Cloudflare dashboard under R2 > `rumaq-receipts` and R2 > `rumaq-brochures` > Settings: "Object access" should be "Private". Receipts are keep-forever user documents; brochures (issue #293) are rotating marketing images swept once no current observation references them and the object is past a one-year review-evidence grace (BROCHURE_GRACE_DAYS), served only through the authenticated Worker proxy `GET /api/brochures/*`.

4. Set Worker secrets:

   ```bash
   ./scripts/deploy.sh cloudflare
   ```

   The deploy script uploads secrets before deploying the Worker so a startup secrets check never fails.

### Secrets management

Generate strong secrets locally:

```bash
openssl rand -hex 32   # WORKER_JWT_SECRET
openssl rand -hex 32   # WORKER_ENCRYPTION_KEY
openssl rand -hex 32   # HAQITA_INGEST_SECRET
```

For local development, copy `backend/.dev.vars.example` to `backend/.dev.vars` and fill in all values. `backend/.dev.vars` is gitignored and must never be committed.

To set or rotate a secret in production:

```bash
# interactive
cf workers secrets update WORKER_JWT_SECRET --worker api --text <value> --type secret_text

# or use the deploy script, which reads secrets from the environment
export WORKER_JWT_SECRET=...
export WORKER_ENCRYPTION_KEY=...
./scripts/deploy.sh cloudflare
```

**Important:** Rotating `WORKER_ENCRYPTION_KEY` invalidates every stored AI API key because they are encrypted with the old key. After rotation, all users must re-enter their AI key in Settings. Rotating `WORKER_JWT_SECRET` only invalidates active sessions; users simply log in again.

| Secret                  | Local | Test | Production | Rotation impact                                  |
| ----------------------- | ----- | ---- | ---------- | ------------------------------------------------ |
| `GOOGLE_CLIENT_ID`      | yes   | no   | yes        | OAuth login only                                 |
| `GOOGLE_CLIENT_SECRET`  | yes   | no   | yes        | OAuth login only                                 |
| `WORKER_JWT_SECRET`     | yes   | yes  | yes        | Active sessions invalidated                      |
| `WORKER_ENCRYPTION_KEY` | yes   | yes  | yes        | Stored AI keys must be re-entered                |
| `HAQITA_INGEST_SECRET`  | yes   | yes  | yes        | Scraper pushes rejected until its env is rotated |

## 9. Free-tier headroom

With ~10 active users and daily use:

- **Workers:** 100k/day ≈ 69 req/min — plenty.
- **D1:** 100k queries/day; a typical session issues ~20 queries.
- **R2:** receipt images are small JPEGs/HEICs; 10 GB holds years of photos.
- **AI cost:** borne by the user, not the platform.

If usage grows, the first upgrade is Workers Paid ($5/mo) for higher request and D1 limits.

## 10. Security checklist

- [x] Session JWT is `HttpOnly`, `Secure`, `SameSite=None`, and signed.
- [x] AI API keys are encrypted at rest (AES-GCM) and only decrypted in the Worker.
- [x] Google OAuth `state` and PKCE verifier prevent CSRF/replay.
- [x] R2 objects are private; frontend receives receipt images through `GET /api/purchases/:id/receipt` (proxy stream). R2 signed URLs are out of current scope (open security item).
- [x] D1 queries are parameterized; no string concatenation.
- [x] Every D1 query that reads or writes household-scoped data filters by `household_id` or `user_id`.
- [x] Same-origin app + API: no cross-origin API calls in production. CORS keeps localhost dev origins allowed and defaults to the canonical `rumaq.ahaqqu.com` origin (`PAGES_ORIGIN` overrides it); unknown origins are rejected.
- [x] AI prompts never expose another user's data and avoid internal DB IDs where possible (`backend/src/__tests__/prompt-isolation.test.ts`).
- [x] General API rate limiting returns 429 with `Retry-After`.

Security summary and runbook: [`docs/SECURITY.md`](SECURITY.md). CORS origin behavior is unit-tested in `backend/src/__tests__/cors.test.ts`.

## 12. Vulnerability management

Two automated mechanisms keep dependencies secure:

| Mechanism                                          | Trigger         | Action                                                                                                                                                                             |
| -------------------------------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dependabot** (`.github/dependabot.yml`)          | Daily 06:00 JKT | Opens PRs for available version bumps, grouped by minor/patch                                                                                                                      |
| **Audit workflow** (`.github/workflows/audit.yml`) | Daily 07:00 JKT | Runs `bun audit`, attempts `bun update`, creates PR with fixes or opens an issue if manual intervention is needed; closes previous `security` issues when the audit is fully clean |

- Production dependencies (`bun audit --omit=dev`) are checked separately and treated as urgent.
- Vulnerabilities that require breaking changes create a GitHub issue (labelled `security`) instead of an auto-PR; the issue is auto-closed once a later audit run passes.
- Transitive packages pinned to vulnerable exact versions by upstreams (`sharp`, `undici`, `zod` under miniflare / `@cloudflare/config`) are held at fixed versions via `overrides` in the root `package.json`.
- Test tooling (`@cucumber/*`, `jest-cucumber`) is kept in `devDependencies` so transitive vulns in those packages never affect production audits.
