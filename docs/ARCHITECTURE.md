# RumaQ — Full-Stack Architecture

This document describes the production architecture for RumaQ on Cloudflare's free tier. The data model is multi-household: users can belong to several households (issue #331 adds the member-management endpoints), while inventory, plans, purchases, and history scope to the active household.

> **Testing strategy has moved** → [`docs/TEST_STRATEGY.md`](TEST_STRATEGY.md)

> **API caching plan (recently implemented)** → [`docs/plans/workers-cache-plan.md`](plans/workers-cache-plan.md)

## 1. Goals & constraints

- **Low friction.** Users photograph receipts; the system infers stock. Manual logging is a fallback, never the default.
- **Cheap to run.** Everything sits on Cloudflare's free tier (Workers with static assets, D1, R2).
- **Privacy first.** Users bring their own AI key. The backend stores it encrypted and only uses it on their behalf.
- **Fast and local-feeling.** The API edge is close to users; the UI stays optimistic and shows loading states that name the work.

## 2. High-level stack

| Layer          | Service                                | Role                                            | Free-tier limit                     |
| -------------- | -------------------------------------- | ----------------------------------------------- | ----------------------------------- |
| Frontend       | Cloudflare Worker (static assets)      | Hosts the React + Vite SPA on the Worker origin | Bundled with the Worker deploy      |
| API            | Cloudflare Workers                     | Hono HTTP API, auth, AI proxy                   | 100,000 requests/day                |
| Database       | Cloudflare D1                          | Relational SQLite database                      | 500 MB storage, 100,000 queries/day |
| Files          | Cloudflare R2                          | Receipt image + document vault storage          | 10 GB storage, 10 M reads/mo        |

| Auth           | Google OAuth 2.0                       | SSO login, managed inside the Worker            | Free                                |
| AI             | OpenAI / Gemini / Anthropic / OpenCode | External LLM calls proxied through the Worker   | User's own billing                  |

### Auth routes

Auth paths (`/api/auth/login`, `/api/auth/callback`, `/api/auth/logout`, `/api/auth/email-login`) are handled directly in the gateway via `authApp.fetch()`. They never enter the cached entrypoint.

### Plugin dispatch and enablement (ahaqqu/RumaQ#435)

Optional features are plugins (plugin architecture: `docs/plan/plugin-architecture.md`), currently only the document vault. The gateway dispatches plugin prefixes through the registry (`backend/src/plugins/registry.ts`) with boundary-aware matching (`path === p || path.startsWith(p + '/')`) — path-only, exactly like the hand-wired core apps. Because the household is unknown until `propsAuthMiddleware` has resolved it, the household-aware **enablement gate installs after auth inside each plugin app**: a disabled (or deployment-off) plugin answers `404 {"error":"Not found"}` for every route in its prefix, fail-closed, with `Cache-Control: private, no-cache`. Two resolution layers with deliberate, opposite failure postures (never unify them):

- **Household enablement** — `household_plugins` rows (migration 0028), one per (household, plugin); an absent row resolves to the manifest's `defaultEnabled`. Read per request (one indexed PK seek), **fails closed** on a read error (privacy posture). Explicit rows always win; there is no grandfathering backfill.
- **Deployment availability** — `deployment_flags` rows (migration 0029), the ops kill-switch (`plugin.<id>.available` = `off`), read once per isolate with a ≤30 s cache, **fails open** on a read error (availability posture — a flags outage must not take the vault down). Flipping it is an UPDATE, not a deploy.

`/api/me` carries an additive `enabledPlugins` array (ids only, keyed to the ACTIVE household). **An absent field means "all catalog plugins enabled"** — legacy clients, a rolled-back deploy, and a failed enablement read all land on that safe default. Advertisement fails open while the route gate still fails closed, so a client can never gain access it lacks. On the frontend (#436), `frontend/src/plugins/` holds the static catalog (one entry per plugin, parity-tested against the server manifests) and the enablement context filters it: a disabled plugin loses its nav entry in the sidebar and mobile drawer, while the page-title lookup is deliberately unfiltered (#466 — a disabled plugin's route still shows its real page title behind the gate); its route renders the disabled empty state instead of the page — it never fetches the gate's 404s. Refetch rides the existing household-switch cache sweep (`useActivateHousehold` invalidates everything, `['me']` refetches, the catalog re-derives).

The settings catalog itself (#437) is a CORE surface, not a plugin: `apps/plugins.ts` (dispatched for `/api/plugins*` ahead of the registry's prefix matching — it must answer even when every plugin is disabled, since it is the thing that re-enables them; the core prefixes the gateway hand-wires — auth, households, tasks, calendar, `/api/plugins` — are reserved in `backend/src/plugins/core-prefixes.ts`, and `validatePluginManifests` rejects any manifest claiming one at build time) serves `GET /api/plugins` — every registered manifest in registry order with each posture layer reported separately (`deployment_available`, `plan_entitled`, `enabled` + `source`, and the §3.3 conjunction as `available`) — and `PUT /api/plugins/{pluginId}/enablement`, the owner-only toggle (`requireOwner`, non-owners get the typed 403). The toggle writes the `household_plugins` row and a `plugin_enabled`/`plugin_disabled` receipt into `household_plugin_audit` (migration 0032 — FK-less, the audit is a receipt, not a child of the household) in ONE batch; setting the state a plugin already resolves to is an idempotent no-op (no row rewrite, no synthetic audit event). In the UI the section lives on the household-admin screen (`plugins/PluginFeatures.jsx`, en "Features" / id "Fitur" — the §8.3 naming): per-plugin copy and capability chips from the static catalog entries, the honest posture line (ops kill-switch, paywall, or the §3.4 retention promise on a disabled plugin), and an owner-only `role="switch"`; members get a read-only state chip. The toggle's mutation updates both the `['plugin-catalog']` and `['me']` caches optimistically (rollback on failure, invalidate on settle), so the nav gating reacts without a reload.

The purge lifecycle (ticket 5, #439) is a JOB, never a request (plan §3.4): `POST /api/plugins/{pluginId}/purge` is the owner-only initiation — a TYPED confirmation (`confirm` must equal the manifest name exactly; a checkbox is a misclick away) that only MARKS the enablement row's `purge_state` (`pending`/`purge_requested_by`, migration 0035) — and the nightly cron's chunk driver (`lib/plugin-purge.ts`, riding the same `scheduled` tick as the #353/#426 sweeps) drains one budgeted chunk per invocation: 40 storage deletes per tick, sized so the free plan's 50-subrequest cap holds (a 200-document vault takes ~5 nightly ticks; the JSON cursor on the enablement row makes tick n+1 resume exactly where n stopped). The chunk reads the keys from `document_files` BEFORE any row goes — the storage port has no `list` by design, so those rows are the only record of where the bytes live — deletes every object through the injected port first, then deletes the document rows + advances the cursor in one guarded batch: bytes-before-rows, idempotent per document, pinned by a detector test that throws if any delete ever fires for an already-erased row. Completion writes ONE `plugin_purged` receipt (0032's CHECK admitted it from day one) with the initiating owner as actor, and the drain clears the plugin's `document_audit` rows. While a drain is pending/running the vault REFUSES uploads (409 write gate, fail-closed) — and the gate is enforced TWICE: once before the 10 MB body is read, and again IN the create/addFile INSERT statements (a body already in flight when the drain started lands nothing). The completion's `drained` verdict is derived from the batch's own `meta.changes`, never from the keyset read — a document the cursor can never reach (an escaped in-flight commit or a same-second smaller-id commit) defeats the guard, reports `drained: false` and clears the cursor for a re-seek, so a `complete` dissolution can never coexist with live bytes. The driver never hands a chunk below the plugin's declared budget floor (`purgeBudgetFloor` — a chunk deletes whole documents), and one failing household is isolated: it logs, retries next night, and the healthy households behind it still drain. The owner's CANCEL lever (`DELETE /api/plugins/{pluginId}/purge`, audited-by-state not by-receipt — the cancel moves no bytes) releases a drain that can never complete (one corrupted `r2_key` throws on every chunk forever), returning the row to the never-requested resting state and lifting the write gate immediately; documents the drain already finished stay gone. Household dissolution is ordered, not cascaded: `drainPluginPurgesForHousehold` is the callable precondition any future delete-household flow must run BEFORE `DELETE FROM households` (the cascade would otherwise erase the only key records and orphan every object — pinned by a test both ways). The grace decision: purge runs IMMEDIATE — DokumenQ's amendment 1 (§9.1.9) set the vault app's `gc_grace_days` to 0 because #388 promises hard delete removes object AND metadata; the `pending` state keeps a future grace window additive (plan §8 Q4). The catalog entry carries the purge slice (`state`/`requested_at`/`completed_at`), the UI adds the owner-only danger action behind the typed-confirmation dialog, and the drain window hides the action while showing the uploads-paused line.

The export capability (ticket 6, #440) is its read-only mirror: `GET /api/plugins/{pluginId}/export` (owner-only, the same `requireOwner` posture — the archive IS the whole household's data in one exfiltration-sized payload, and §3.4 routes delete through export-first in the same owner-only lifecycle UI). It is NOT gated with purge — reads stay open while a drain runs, and exporting what the drain has not reached yet is exactly the point. Core owns WHEN/authz (the capability check, the owner gate, `EXPORT_ARCHIVE_FILE_BUDGET` = 40 files per archive — the free plan's 50-subrequest cap holds: ≤4 D1 statements + 40 storage reads); the plugin owns HOW through the `PluginExportJob` registration seam (`plugins/documents/export.ts`, the `PluginPurgeJob` split). The archive is a stored (uncompressed) ZIP written by `lib/zip.ts` — dependency-free by the ticket's acceptance criterion (fflate exists only as @vitest/ui's transitive devDependency; importing it would ADD a third-party dependency) — streaming with lazy per-file loaders: each R2 get happens as the body drains, peak memory is the largest single file (≤10 MB), never the vault. It carries the bytes at `files/<document>/<sort>-<name>`, `documents.csv` + `files.csv` (RFC 4180, UTF-8 + BOM, the #422 free-text names, no `r2_key` — an internal handle the client must not learn; `archive_path` replaces it) and a trailing `manifest.json` whose counts report what the stream DELIVERED (a 0-byte entry where `files.csv` reports `size_bytes > 0` marks bytes unavailable at export time — missing object or namespace-guarded key, the skip-with-note state so a half-dead vault still exports; audit rows are internal receipts and are NOT included). Whole documents only (the purge chunk's discipline), so a vault over the 40-file budget chains sequential downloads via the `X-Export-Next-Cursor` header — the cursor is base64url JSON bound to the issuing household (a foreign one is a 400, never a silently wrong slice) with the same (created_at, id) keyset the purge cursor uses. Every archive writes ONE `plugin_exported` receipt into `household_plugin_audit` (migration 0036 widened the CHECK — the 0025 table-rebuild precedent) with the owner as actor.

Plugin-declared cron tasks (ticket 7, #441) ride their OWN nightly trigger, not the core tick: the Worker carries TWO `triggers.scheduled` entries (the strings live in `backend/src/cron-schedules.ts`, one source shared by `cloudflare.config.ts` and the dispatch), and the split is a hard subrequest constraint — the core tick's worst case is 48/50 with one purge-capable plugin (the purge accounting above), so plugin tasks get a SECOND invocation with a fresh 50-subrequest budget instead of competing for the core's. `gateway.scheduled` tells them apart via `ScheduledController.cron`: the plugin-tasks schedule (`43 3 * * *`) runs ONLY `lib/plugin-cron.ts`'s driver; anything else (including no cron at all) falls through to the core tick — the safe default, never the fan-out. The MANIFEST declares each task as pure data (`name` — a unique snake_case slug, validated like capabilities — plus `scope: 'global' | 'household'`), the REGISTRATION binds each declared name to its handler (`cronTaskHandlers`); a declared-without-bound (or bound-without-declared) drift is caught at build time by `cronTaskBindingViolations` (pinned against the real registry) and soft-guarded at runtime (logged, counted, never thrown). ISOLATION IS THE CONTRACT (§4.4): every task — and every household within a household-scoped task — runs under its own try/catch; a poisoned task fails ITS plugin/household for the night (a structured `[plugin-cron]` log line, retried next tick) while every other plugin's task, and the core tick on the other trigger, continue untouched. Enablement is per household by the §4.3 truth table: a 'household' task iterates the plugin's enabled set resolved from ONE query per defaultEnabled branch (`resolveEnabledHouseholdIds` in `plugins/enablement.ts` — explicit rows win, an absent row falls to the manifest default), a 'global' task ignores enablement entirely, and an enabled-set read error fails CLOSED for that plugin's task only (skipped for the night, logged). The failure artifact is the log line — no failure rows (the 0032 lifecycle vocabulary is the closed enablement/purge domain; the next free migration slot takes a durable record if one is ever wanted). The purge job STAYS on the core tick beside this driver, not under it — its object budget, budget floor and cancel race are purge-specific semantics. No shipped plugin declares a task yet, so the second invocation is a no-op nightly until the first declaration lands (the driver's own fixed spend is one enabled-set read per household-scoped task; today it costs zero subrequests).

### Caching

- **Public routes** (`/api/health`, `/api/auth/email-status`): `Cache-Control: public, max-age=60`
- **Authenticated routes** (`/api/me`, `/api/stock`, etc.): `Cache-Control: private, no-cache` — never cached at the edge, every request runs through the Worker to verify auth.
- **Error responses**: `Cache-Control: private, no-cache`

Receipt images flow through the Worker into R2. The Worker returns signed URLs so the frontend never talks to R2 directly.

## 5. Authentication

Google OAuth 2.0 is implemented inside the Worker using the [Authorization Code flow](https://developers.google.com/identity/protocols/oauth2/web-server) with PKCE.

1. `GET /api/auth/login`
   - Generates a `state` nonce and PKCE `code_verifier`.
   - Stores the verifier in a short-lived signed cookie.
   - Redirects the browser to Google's authorization endpoint.

2. `GET /api/auth/callback`
   - Validates the `state` parameter.
   - Exchanges the authorization code for an access token.
   - Fetches user info (`email`, `name`, `picture`, `sub`) from Google's userinfo endpoint.
   - Upserts the user in D1.
   - Issues a long-lived signed JWT in an `HttpOnly`, `Secure`, `SameSite=None` cookie named `rumaq_session`.

3. `GET /api/auth/logout`
   - Clears the session cookie and redirects to the app origin.

4. Protected-route middleware
   - The **gateway** (`backend/src/gateway.ts`) routes `/api/*` non-auth requests to the `CachedApi` entrypoint (which wraps `apiApp`).
   - Inside `apiApp` (`backend/src/apps/api.ts`), the `propsAuthMiddleware` first checks `c.env.props` (fast path when props are provided), then falls back to reading the `rumaq_session` cookie, verifying the JWT, and resolving the active household: `user_settings.active_household_id` wins only while the user is still a member of that household (a stale pointer after a removal must not grant access), otherwise the oldest `household_members` row. It sets Hono `Variables` (`userId`, `householdId`) for downstream route handlers. Routes that require authentication register this middleware; public routes skip it entirely.
   - Household member management (issue #331) is a separate domain app (`backend/src/apps/households.ts` + `backend/src/lib/households.ts`) the gateway dispatches for `/api/households*` before the `apiApp` fallthrough — same CORS/per-IP rate-limit/auth stack, plus owner/last-owner rules and expiring invite codes in `household_invites` (migration 0020). Members come in two modes (issue #388, migration 0021): linked to a user account, or profile-only (`user_id` NULL — no account, forced role `member`, owner-managed, never authenticates); every member row carries a surrogate `id` that member-addressed endpoints (`PATCH`/`DELETE .../members/{memberId}`, profile-only creation via `POST .../members`) and the future document vault key on. Link-later (issue #397, migration 0023): an invite can carry `target_member_id` marking one profile-only member; redeeming it attaches the redeemer's `user_id` to that row (`UPDATE ... WHERE user_id IS NULL` + pre-check/guard so races report typed 4xx, never a partial-unique-index 500) instead of inserting a new member — the row's id and profile fields survive, so vault documents stay attached. The invite CASCADE-deletes with its target member (transient data).

**Why not Cloudflare Access?** Access is simpler, but in-app OAuth keeps the API self-contained, lets us store the user record in D1 for personalization, and makes local development straightforward with the Cloudflare Vite plugin.

### Email/password auth (testing mode)

A second auth method is available for testing, gated behind the `EMAIL_AUTH_ENABLED` env variable. Google OAuth remains the primary production path.

1. `GET /api/auth/email-status`
   - Public endpoint returning `{ enabled: boolean }` so the frontend can decide whether to render the email form.

2. `POST /api/auth/email-login`
   - Enabled only when `EMAIL_AUTH_ENABLED === 'true'` (otherwise returns 403).
   - Validates `email` + `password` against the `password_hash` column on the `users` table (PBKDF2-SHA256, 100k iterations).
   - Onboards a new user with the same household/seed logic as the Google callback.
   - Issues the same `rumaq_session` JWT cookie.

### Admin access

Operator-only surfaces (`/api/admin/*`: the price monitor, Scrape Now queue, match review) are gated by the `requireAdmin` middleware, which reads `users.is_admin` (migration 0014) — the flag is the single source of truth and there is no environment fallback. `/api/me` exposes it as `isAdmin`.

Grant or revoke with a one-statement SQL runbook against the production D1 database; no redeploy is needed because the flag is read per-request. Matching folds case (`lower(email)`) because the OAuth callback stores the Google-provided email verbatim:

```bash
# grant
cf d1 execute rumaq --remote --command "UPDATE users SET is_admin = 1 WHERE lower(email) = lower('…');"
# revoke
cf d1 execute rumaq --remote --command "UPDATE users SET is_admin = 0 WHERE lower(email) = lower('…');"
```

One-time cleanup after this ships: the former `ADMIN_EMAILS` Worker secret stops being read but `scripts/deploy.sh` never deletes secrets — remove it manually with `cf workers secrets delete ADMIN_EMAILS`.

## 6. Database

Cloudflare D1 runs SQLite at the edge. The schema is relational and normalized so the same Worker can serve a single household today and multiple households later without rewrites.

See [`backend/migrations/0001_schema.sql`](../backend/migrations/0001_schema.sql) for the full DDL.

Core entities:

- `users` — Google-authenticated accounts.
- `households` + `household_members` — one or more households per user.
- `locations`, `stores` — household-scoped lookup lists.
- `items` — canonical product catalog inside a household.
- `stock` — current on-hand quantity, expiry, run-out estimate.
- `purchases` + `purchase_items` — receipt history; the substrate for all estimates.
- `plans` + `plan_items` — AI-generated shopping trips.
- `user_settings` — AI provider/key, motion preference, currency, and persona roles.
- `documents` + `document_files` + `document_audit` — the household document vault (ahaqqu/RumaQ#388, reworked by #422 / migration 0025, expiry metadata by #426 / migration 0026): free-text document names, one document holding up to 20 files (each its own private R2 object with an optional label), files optionally attached to a member (both modes — linked accounts and profile-only members from 0021), optional expiry metadata (`expires_on` ISO date + `remind_days_before` window — the 30 default is app-level, applied when an expiry is set without one; `days_until_expiry` is computed at read time on the household calendar (pinned UTC+7/WIB — the Indonesia-first audience; one helper feeds the chip, the expiring_within horizon and the nightly sweep), never stored), and a per-action audit trail that outlives the document it records. The daily cron piggybacks the renewal-reminder sweep (issue #426): it computes the per-household due set — documents whose distance has entered their own window — and logs the summary; v1 renders it in-app only (no new notification channel).
- `household_calendar_events` + `household_calendar_event_members` + `household_calendar_event_audit` — the shared family calendar (ahaqqu/RumaQ#430, migration 0031): a core domain app (`backend/src/apps/calendar.ts`, dispatched for `/api/calendar*` like tasks — not a plugin), free-text titled events with an optional HH:MM time and per-member visibility (`all`, or `members` = the listed members plus the creator, with the household owner always reading/managing — the manageability fallback that keeps creator-less or self-excluding events administrable). The endpoint serves a UNION: stored events joined with deadline entries **derived on read** from `documents.expires_on` (#426) — no stored copy to drift, an expiry edit shows on the next read, and `remind_days_before` drives each entry's `due_soon` flag. Indonesian moments (school enrollment, mudik prep, annual tax, birthdays) are quick-add templates in the UI that pre-fill the create form, not schema rows. Mutations are guarded with an in-batch gated audit (the vault/tasks discipline); the audit trail outlives the deleted event.
- `ai_usage_events` — one row per completed AI call (provider, model, input/output/cached tokens, key source); auto-deleted after one year by the daily retention cron.
- `household_plugins` — per-household plugin enablement rows (ahaqqu/RumaQ#435, migration 0028): one row per (household, plugin) with `status` enabled/disabled and a small non-secret `config_json`; an absent row resolves to the plugin manifest's `defaultEnabled`. Read by the plugin gate (fail-closed); written by the owner-only toggle (#437 — the catalog PUT, which batches the row with its lifecycle audit receipt). Migration 0035 (#439) appended the purge state machine to the SAME row — `purge_state` (`pending`/`running`/`done`), the JSON `purge_cursor`, and the requested/completed timestamps — plus a PARTIAL index (`idx_household_plugins_purging`, rows only while a drain is in flight) so the nightly work-set seek never scans the table.
- `household_plugin_audit` — the core plugin-lifecycle receipt table (ahaqqu/RumaQ#437, migration 0032): `plugin_enabled` / `plugin_disabled` rows from the settings catalog's toggle (ticket 5's purge adds `plugin_purged`, already admitted by the CHECK). Household and actor are PLAIN handles with no FK — deleting a household cascades `household_plugins` but can never erase the record that a plugin was toggled (an audit row is a receipt, not a child of the household, plan §3.4).
- `deployment_flags` — the ops kill-switch key/value table (ahaqqu/RumaQ#435, migration 0029): `plugin.<id>.available` = `on`/`off`, read once per isolate with a ≤30 s cache, fail-open (availability posture — the deliberate opposite of household enablement's fail-closed privacy posture).

### Migrations

Schema lives in numbered SQL files under [`backend/migrations/`](../backend/migrations/) — `NNNN_description.sql`, applied in filename order. D1 tracks which files it has already applied (its `d1_migrations` table), so deploys only run the new files.

- **When they run:** automatically on every deploy — `scripts/deploy.sh` runs `cf d1 migrations apply` against the local dev D1 (`--local --persist-to backend/.cloudflare/state`), the production database, and the shared `rumaq-preview` database for branch previews.
- **Writing one:** take the next free number and never edit an applied migration (the recipe is in [`docs/BACKEND_CONVENTIONS.md`](BACKEND_CONVENTIONS.md)). Prefer additive changes (new table/column/index); there are no down migrations — a bad migration is reverted by a forward fix.
- **Testing:** `backend/src/__tests__/migrations.test.ts` applies the full chain to a real SQLite engine (`node:sqlite` — D1 is SQLite); rebuild-style migrations (0021) carry before/after assertions there, and the restore drill (below) round-trips the whole chain through a dump.

## 7. AI integration

Users supply their own API key in Settings. The frontend sends it to the Worker, where it is encrypted with `WORKER_ENCRYPTION_KEY` (AES-GCM via Web Crypto) before being stored in D1. The Worker decrypts it only when making an AI call on the user's behalf.

AI lanes (MVP):

1. **Receipt → stock.** Image uploaded to R2; Worker sends the image URL + prompt to the user's chosen LLM and returns parsed line items for confirmation.
2. **Plan a trip.** Worker asks the LLM to build a shopping plan from low stock + expiry + history.
3. **Chat assistant.** The Worker proxies a chat request; the system prompt includes the user's persona setting.
   > **Tech debt:** Streaming is deferred. The current implementation returns the full response body. See `backend/src/lib/chat.ts` — `sendChatMessage` calls `completeText` (completion, not streaming). The persona system prompt is EN-only (single locale); see `backend/src/lib/persona.ts`.

Every completed AI call is recorded as one row in `ai_usage_events` (per-call granularity — what the 24h/7d/30d admin analytics and per-user cache hit rates need). Usage never caps a call: BYOK is the norm and the shared server key (`RUMAQ_SERVER_AI_PROVIDER`/`RUMAQ_SERVER_AI_KEY`) is uncapped too (issue #353). Retention: a daily cron (`gateway.scheduled`, `cloudflare.config.ts`) deletes events older than 365 days. The user can pick the model (`ai_model`) and a thinking level (`ai_thinking_level`) per provider, mapped to each API's reasoning controls.

### Production deployments

Production deploys to `main` are **commit-based**: `.github/workflows/deploy.yml` triggers on every push to `main` (and on demand from the Actions tab for redeploys). Its first job runs the same CI gate as PRs (`scripts/github/ci.sh`), and the `deploy` job — gated by `needs: ci` — invokes the same `./scripts/deploy.sh cloudflare` used locally. Because both jobs live in a push-triggered workflow, CI and deploy status are visible on the commit itself. Pull requests use `.github/workflows/ci.yml` instead, which has no deploy job, so PR checks never show a deploy entry.

Rapid merges queue on the `deploy-main` concurrency group and deploy sequentially. When the changes since the **last successful deploy** only touch deploy-irrelevant files (Markdown, `docs/`, `.github/`, license/attribute files), `scripts/github/needs-deploy.sh` skips the deploy — a deliberate, visible skip; anything else deploys. Basing the skip decision on the last deployed commit (queried via the GitHub API) rather than the previous push means docs-only pushes and dropped queued runs can never hide a pending code change: the next deploy's diff still contains them. Production deploys always use the `rumaq` D1 database configured by `CLOUDFLARE_DATABASE_ID`.

The Deploy production step's env carries only the Cloudflare credentials and the four gateway secrets. `HAQITA_INGEST_SECRET` is deliberately **not** passed and never written by CI (#456): it is set and rotated out-of-band by the operator, so a deploy can never clobber the rotated Worker value. `scripts/test/deploy-secrets.sh` (run by `scripts/github/ci.sh`) fails on drift.

### Branch deployments

When not on `main`, `./scripts/deploy.sh cloudflare` deploys to a **branch-specific Worker** (`rumaq-api-{sanitized-branch}`) that serves both the SPA (static assets) and the API. This gives a branch its own real preview environment at a single URL, backed by a real Worker, rather than pointing the preview frontend at the production Worker. Previews are deployed **on demand** via `workflow_dispatch` — not every PR gets one automatically.

Pull request previews use a dedicated **staging D1 database** (`rumaq-preview`) so preview data never touches production. The preview database is created once and shared across all PR previews. Production deploys continue to use the `rumaq` database configured by `CLOUDFLARE_DATABASE_ID`.

Branch Workers are cleaned up automatically via `.github/workflows/cleanup-branch.yml` when the PR is closed. `scripts/cleanup-preview-workers.sh` deletes all `rumaq-api-*` preview Workers at once if orphans ever accumulate.

`.github/workflows/preview.yml` runs only on `workflow_dispatch`. It deploys the branch Worker and comments the preview URL on the PR when one is open for the branch.

### Secrets management

Generate strong secrets locally:

```bash
openssl rand -hex 32   # WORKER_JWT_SECRET
openssl rand -hex 32   # WORKER_ENCRYPTION_KEY
openssl rand -hex 32   # HAQITA_INGEST_SECRET
```

For local development, copy `backend/.dev.vars.example` to `backend/.dev.vars` and fill in all values. `backend/.dev.vars` is gitignored and must never be committed.

To set or rotate a secret in production:

```bash
# interactive
cf workers secrets update WORKER_JWT_SECRET --worker api --text <value> --type secret_text

# or use the deploy script, which reads secrets from the environment
export WORKER_JWT_SECRET=...
export WORKER_ENCRYPTION_KEY=...
./scripts/deploy.sh cloudflare
```

`HAQITA_INGEST_SECRET` is never part of that path — set and rotate it out-of-band only. Three copies must move in the same window, and CI updates none of them:

1. **the Worker secret** (the authority) — `cf workers secrets update`, below;
2. **the pipeline box's env** (`RUMAQ_INGEST_SECRET` in the private pipeline repo);
3. **the GitHub repo secret of the same name** — read-only, used only by the 6-hourly Production Smoke freshness check (`scripts/github/check-price-freshness.sh`). Leave it stale and that step fails 401 on every run and opens a `Smoke test failure` issue a day; update it with the rotation, or delete it to disarm the staleness alert.

An ordinary deploy preserves the Worker secret: the deploy uploads only the gateway secrets, and Cloudflare merges them into the existing set (`PATCH …/workers/scripts/<worker>/secrets-bulk` with `application/merge-patch+json`), so an unlisted secret is never deleted. A Worker _recreated_ from scratch — deleted, or renamed — does come back without it, and CI will never restore it; re-run the command below, and until then the ingest surface answers 503 `Ingest endpoint not configured` rather than 401.

```bash
cf workers secrets update HAQITA_INGEST_SECRET --worker api --text <value> --type secret_text
```

For a rotation that does not 401 the nightly at all, use the successor secret the ingest middleware already accepts — in this order:

```bash
cf workers secrets update HAQITA_INGEST_SECRET_NEXT --worker api --text <new> --type secret_text   # 1. Worker accepts both
# 2. point the box at <new> and let one nightly run succeed
cf workers secrets update HAQITA_INGEST_SECRET      --worker api --text <new> --type secret_text   # 3. promote
cf workers secrets delete HAQITA_INGEST_SECRET_NEXT --worker api                                   # 4. close the window
```

`requireIngestSecret` (`backend/src/apps/api.ts`) accepts every non-empty candidate while both exist, so no step has a mismatched window. Nothing promotes `_NEXT` automatically: the deploy writes neither secret, so every step is the operator's.

**Important:** Rotating `WORKER_ENCRYPTION_KEY` invalidates every stored AI API key because they are encrypted with the old key. After rotation, all users must re-enter their AI key in Settings. Rotating `WORKER_JWT_SECRET` only invalidates active sessions; users simply log in again.

| Secret                  | Local | Test | Production | Rotation impact                                  |
| ----------------------- | ----- | ---- | ---------- | ------------------------------------------------ |
| `GOOGLE_CLIENT_ID`      | yes   | no   | yes        | OAuth login only                                 |
| `GOOGLE_CLIENT_SECRET`  | yes   | no   | yes        | OAuth login only                                 |
| `WORKER_JWT_SECRET`     | yes   | yes  | yes        | Active sessions invalidated                      |
| `WORKER_ENCRYPTION_KEY` | yes   | yes  | yes        | Stored AI keys must be re-entered                |
| `HAQITA_INGEST_SECRET`  | yes   | yes  | yes        | Scraper pushes rejected until its env is rotated |

`HAQITA_INGEST_SECRET` is the exception to deploy-managed rotation: it is set and rotated out-of-band (`cf workers secrets update`, above) and the CI deploy deliberately never writes it (#456). It is also absent from `backend/cloudflare.config.ts`'s declared bindings for the same reason.

### Database backups & restore

Nightly automated backup (ahaqqu/RumaQ#342): the scheduled **D1 backup** workflow (`.github/workflows/backup.yml`, 20:07 UTC = 03:07 WIB, plus manual dispatch) exports the production D1 database via the REST API and uploads the dump into the private `rumaq-receipts` bucket under `backups/<db>/<WIB-date>/dump.sql` — a keyspace no Worker binding can read. Retention keeps the newest 14 daily and 4 weekly (Sunday) dumps, pruned by `scripts/backup/export-d1.sh` on the success path only — a failed backup never deletes the previous ones. A failed run opens a `backup-failure` issue; the next green run closes it (the smoke-test pattern).

Before any dump may be imported back into production it must pass the **restore drill**: `./scripts/backup/restore-drill.sh <dump.sql>` rebuilds the file in scratch SQLite and asserts `integrity_check`, `foreign_key_check`, and the canary tables (users, households, household_members, stock, purchases, documents). The drill engine is tested against the real migration chain in `backend/src/__tests__/d1-restore.test.ts`; run the drill monthly against the newest R2 dump so restore-rot is caught while the backup is still in its Time Travel window.

The full runbook — Time Travel for recent accidents (Scenario A), dump → drill → fresh DB → cutover for older disasters (Scenario B) — plus the owner actions if the API token's grants turn out to be incomplete, live in [`docs/plan/d1-backup.md`](plan/d1-backup.md). The workflow reuses the deploy credential trio (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`); a scoped `BACKUP_CLOUDFLARE_API_TOKEN` is preferred when present.

## 9. Free-tier headroom

With ~10 active users and daily use:

- **Workers:** 100k/day ≈ 69 req/min — plenty.
- **D1:** 100k queries/day; a typical session issues ~20 queries.
- **R2:** receipt images are small JPEGs/HEICs; 10 GB holds years of photos.
- **AI cost:** borne by the user, not the platform.

If usage grows, the first upgrade is Workers Paid ($5/mo) for higher request and D1 limits.

## 10. Security checklist

- [x] Session JWT is `HttpOnly`, `Secure`, `SameSite=None`, and signed.
- [x] AI API keys are encrypted at rest (AES-GCM) and only decrypted in the Worker.
- [x] Google OAuth `state` and PKCE verifier prevent CSRF/replay.
- [x] R2 objects are private; frontend receives receipt images through `GET /api/purchases/:id/receipt` (proxy stream). R2 signed URLs are out of current scope (open security item).
- [x] Document vault bytes stream only through the household-scoped, per-file `GET /api/documents/{id}/files/{fileId}/content` (#422 — a document holds up to 20 files; auth + `household_id` in the SQL predicate, and the file must belong to the named document; foreign ids answer 404 with no existence leak). Uploads are capped at 10 MB per file (Content-Length pre-check + post-parse), magic-byte sniffed (declared-vs-actual mismatch = 415), and audited; no public or presigned URLs exist for documents.
- [x] Plugin enablement is enforced server-side (#435): the household-aware gate sits after auth inside each plugin app and answers 404 fail-closed on a disabled household (privacy posture) or an enablement read error, while the deployment flag (`deployment_flags`) fails open on a read error (availability posture). The two postures are documented in `backend/src/plugins/` and never unified. `/api/me`'s `enabledPlugins` is advertisement only — enforcement never rides it.
- [x] The plugin import boundary is test-enforced (`plugin-boundary.test.ts`, #435): plugin code imports core's published API (the `plugins/` root modules), its own module, and `env.DB` — nothing else; the allow-list is per-plugin (a `pluginId → imports` map — a new plugin starts empty and inherits nothing) and the documents entry names exactly the core surface the vault consumes (empty until ticket 4 #438 re-homed the vault, which is the reviewed decision that filled it) and every rule demonstrably fires in the test.
- [x] D1 queries are parameterized; no string concatenation.
- [x] Every D1 query that reads or writes household-scoped data filters by `household_id` or `user_id`.
- [x] Same-origin app + API: no cross-origin API calls in production. CORS keeps localhost dev origins allowed and defaults to the canonical `rumaq.ahaqqu.com` origin (`PAGES_ORIGIN` overrides it); unknown origins are rejected.
- [x] AI prompts never expose another user's data and avoid internal DB IDs where possible (`backend/src/__tests__/prompt-isolation.test.ts`).
- [x] General API rate limiting returns 429 with `Retry-After`.

Security summary and runbook: [`docs/SECURITY.md`](SECURITY.md). CORS origin behavior is unit-tested in `backend/src/__tests__/cors.test.ts`.

## 12. Vulnerability management

Two automated mechanisms keep dependencies secure:

| Mechanism                                          | Trigger         | Action                                                                                                                                                                             |
| -------------------------------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dependabot** (`.github/dependabot.yml`)          | Daily 06:00 JKT | Opens PRs for available version bumps, grouped by minor/patch                                                                                                                      |
| **Audit workflow** (`.github/workflows/audit.yml`) | Daily 07:00 JKT | Runs `bun audit`, attempts `bun update`, creates PR with fixes or opens an issue if manual intervention is needed; closes previous `security` issues when the audit is fully clean |

- Production dependencies (`bun audit --omit=dev`) are checked separately and treated as urgent.
- Vulnerabilities that require breaking changes create a GitHub issue (labelled `security`) instead of an auto-PR; the issue is auto-closed once a later audit run passes.
- Transitive packages pinned to vulnerable exact versions by upstreams (`sharp`, `undici`, `uuid`, `zod` under miniflare / `@cloudflare/config`) are held at fixed versions via `overrides` in the root `package.json`.
- Dev-tooling advisories without an in-range upstream fix are held there too: `deepmerge` 4.1.2 is a deliberate downgrade (no patched release exists for GHSA-gcqx-w48m-w2h4, so 4.1.2 is the highest release outside the vulnerable range; its sole consumer, `@rollup/plugin-node-resolve`, only performs a plain two-object merge), while `glob` 14.0.3 and `minimatch` 11.0.4 force the upstream fix releases across the majors consumers declare (GHSA-3g3m-2fjr-6pw4, GHSA-g3hv-75wg-m249).
- Test tooling (`@cucumber/*`, `jest-cucumber`) is kept in `devDependencies` so transitive vulns in those packages never affect production audits.
